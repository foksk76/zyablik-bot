# ADR-0045: Файл конфигурации как источник правды

## Статус

Принято.

## Дата

2026-08-03

## Контекст

Конфигурация bot-platform и queue-monitor задаётся только через
env-переменные:

- `createBotPlatformConfig` (`src/bot-platform/core/config.js:27`) читает
  `process.env` с дефолтами и валидацией;
- `createQueueMonitorConfig` (`src/queue-monitor/config.js:7`) — отдельный
  модуль, тоже env-based;
- секреты (`MAX_BOT_TOKEN`, `METRICS_API_KEY`, `SESSION_SECRET`,
  `IDP_CLIENT_SECRET`) лежат в `.env`;
- установка/изменение конфигурации = правка `.env`/`export` + рестарт
  (INSTALL.md, runbooks).

Планируется web UI для просмотра/изменения/применения конфигурации и
импорт/экспорт файла конфигурации (idea: `docs/ideas/config-file-and-schema-driven-settings.md`),
а также переход установки на docker compose. Два целевых требования
конфликтуют с env-only моделью:

1. **UI управляет конфигурацией** — нужен машиночитаемый источник правды,
   который UI может читать и писать, а не разрозненный набор env-переменных
   без схемы;
2. **docker compose** — конфигурация должна жить в volume и передаваться в
   контейнер, секреты — через docker secrets/env.

### Проблема

- Env не является артефактом, который можно валидировать, диффовать,
  версионировать и выгружать/загружать целиком;
- UI не может осмысленно управлять конфигурацией без единой схемы и файла;
- при docker compose `.env`-подход фрагментируется между compose-файлом и
  переменными окружения процесса.

### Требования

1. Единый источник правды — файл конфигурации (JSON);
2. Обратная совместимость точки входа: процесс по-прежнему можно запускать
   без файла (дефолты) — но при наличии файла он главный;
3. Секреты не хранятся в файле открытым текстом: значения живут в
   `.env`/docker secrets (этап развёртывания), в файле — только `$VAR`-ссылки;
4. Конфигурация применима на работающем процессе через рестарт
   (Stage → Apply → рестарт);
5. Дизайн-ограничение: конфигурация работает в docker compose (volume + env);
6. Ноль новых внешних зависимостей (ADR-0015): JSON-парсинг и валидация — stdlib.

## Решение

Ввести **`zyablik.config.json`** как источник правды для управляемых
настроек. `config.js` переписывается на трёхслойный мерж:

```text
defaults → файл конфигурации → .env (bootstrap + секреты + неизменяемая база)
```

`.env` остаётся как слой этапа развёртывания и содержит только:

- **Bootstrap:** `ZYABLIK_CONFIG` (путь до файла);
- **Node runtime:** `NODE_EXTRA_CA_CERTS` (TLS-доверие, глотается Node до
  старта процесса);
- **Секреты:** `MAX_BOT_TOKEN`, `METRICS_API_KEY`, `SESSION_SECRET`,
  `IDP_CLIENT_SECRET`;
- **Неизменяемая база:** `MAX_API_URL`, `IDP_ISSUER`, `IDP_CLIENT_ID`,
  `IDP_REDIRECT_URI`, `IDP_AUDIENCE`.

Всё, чем управляет оператор (транспорт, очередь, ingress, monitor,
rate-limit, логи, IdP-настройки рантайма, плагины), — в файле. **При наличии
файла управляемые env-переменные не читаются** (тихо игнорируются):
конфликт решает файл, старые env-значения его не переопределяют. Совместимость
с docker compose ключевая: при контейнерной установке `.env`-слой =
переменные окружения контейнера / docker secrets.

- Путь до файла: env-переменная `ZYABLIK_CONFIG`, по умолчанию
  `./config/zyablik.json`;
- `createBotPlatformConfig(environment)` и `createQueueMonitorConfig(environment)`
  заменяются единым `loadConfig(options)`; каждый модуль читает свою секцию
  из одного результата: `bot`, `queue`, `ingress`, `monitor`, `plugins`;
- Валидация — единая схема секций в stdlib, без сторонних схемных движков.
  Формат схемы поля определён в ADR-0046 (тип, default, required, secret,
  enum, min/max, nullable, description, section) — одна декларация
  используется и для валидации файла, и для рендера форм в UI.
- Секции файла: `bot`, `queue`, `ingress`, `monitor`, `plugins`. Настройки
  плагина — в секции `plugins.<имя>.*` (например `plugins.identity.*`);
  схема плагина объявляет свою ветку в merged-схеме под тем же ключом
  (ADR-0046). Секции параметров Zabbix Media type **не будет** — эти значения
  живут на стороне Zabbix, бот ими не управляет; дублирование создало бы
  второй источник правды.

### Секреты

Секретные **значения** живут в `.env` (этап развёртывания) / docker secrets
и в файл не попадают. В файле секрет задаётся **`$VAR`-ссылкой**, например
`"maxBotToken": "$MAX_BOT_TOKEN"`; при загрузке ссылка резолвится из
`process.env` (в docker compose — из окружения контейнера).

- Ключи с `secret: true` никогда не попадают в файл открытым текстом
  (экспорт редактирует, API не возвращает значения, логи маскируются —
  ADR-0013);
- **UI секреты не редактирует** (решение по idea, «только просмотр статуса»):
  web UI показывает только факт «задан / не задан» и маску (`••••`); ни
  значение, ни имя `$VAR`-ссылки через UI не меняются — они задаются в
  `.env`/docker secret при деплое;
- Неразрешённый `$VAR` для секрета — fail-fast при старте, для остальных
  ключей — warn + default;
- Литеральное значение в secret-поле — **невалидно**: секрет задаётся только
  `$VAR`-ссылкой или пустым значением. Правило применяется на всех уровнях:
  валидация файла при старте (конфиг с литеральным секретом не загружается,
  срабатывает авто-откат), pre-validate на Apply и импорт (reject со списком
  полей, ADR-0046).

### Применение изменений

Stage → Apply → рестарт процесса. Apply включает **предварительную
валидацию** и **авто-откат к last-known-good** (вариант A):

- **Staged** — изменения, сохранённые из UI, ещё не в файле;
- **Apply (pre-validate)** — перед записью staged валидируется: схема
  (ADR-0046) + резолв `$VAR` fail-fast + dry-run (старт в режиме проверки).
  При ошибке Apply отклоняется, рестарт не инициируется, оператор видит
  ошибку (поле + причина) в UI. Плохой конфиг не доходит до рестарта;
- **Apply (применение)** — после успешного pre-validate: текущий файл
  копируется в `zyablik.config.json.lkg`, новый записывается атомарно
  (temp+rename), инициируется корректный рестарт процесса через
  сервис-менеджер. Процесс один и владеет ingress/worker/monitor, поэтому
  полный рестарт применяет все изменения. Рестарт делегируется наружу
  (systemd `Restart=always` + `RestartSec` + `StartLimitBurst`, или внешний
  `systemctl restart`; docker `restart: unless-stopped` либо рекреация
  контейнера). `Restart=on-failure` для apply-рестарта **не подходит**: он
  срабатывает только при ненулевом exit-коде, а self-restart после Apply —
  чистый exit 0 (обоснование и примеры — idea-документ, Open Questions).
  SIGTERM-хендлеры корректного завершения уже есть (ADR-0033);
- **last-known-good** — копия активного файла перед применением
  (`zyablik.config.json.lkg`);
- **Авто-откат при старте** — стартовый детектор срабатывает по двум
  детерминированным условиям; рантайм-краш сам по себе откат НЕ вызывает
  (иначе OOM/занятый порт ложно откатывали бы хороший конфиг):
  1. **Валидационный отказ** — `zyablik.config.json` не проходит валидацию
     (схема, `version`, `$VAR`-резолв, литеральный секрет): файл карантинится
     в `zyablik.config.bad.json`, восстанавливается `zyablik.config.json.lkg`,
     процесс стартует с lkg. Порядок старта: plugin-loader собирает
     merged-схему (система + плагины) → детектор валидирует файл по этой
     схеме → старт. Структурные ошибки (JSON, `version`, литеральные
     секреты) детектируются на любом шаге;
  2. **Подтверждающий режим (pending-маркер)** — Apply перед рестартом
     записывает `zyablik.config.json.pending` (хеш применяемого файла).
     Процесс стартует с нового конфига; по выходу на **ready** — HTTP-серверы
     (ingress/dashboard) подняты и загрузка завершена, окно `StartupWait`
     по умолчанию 30с — маркер удаляется, конфиг закреплён. Если процесс
     завершился до ready (ненулевой exit) — маркер остаётся, и при
     следующем запуске (системd `Restart=always` / docker
     `unless-stopped` перезапустят процесс) детектор откатывает к lkg и
     снимает маркер;
  lkg перед восстановлением проходит ту же валидацию (схема/`version`/
  `$VAR`). Если и lkg невалиден — процесс отказывается стартовать
  (fail loudly), рестарт-политика ограничивает цикл (`StartLimitBurst` /
  docker `max-retries`), чтобы не было crash-loop;
- **Rollback (ручной)** — кнопка в UI восстанавливает lkg и рестартует.
  Ручной rollback **снимает pending-маркер** (если он был установлен
  незавершённым Apply): откат — это явное решение оператора, конфиг lkg
  восстанавливается сразу, подтверждение не требуется. Если маркер был
  установлен, восстановление lkg делает его неактуальным — детектор не
  должен повторно откатывать уже откаченный конфиг при следующем старте.

Хранение staged-состояния — **отдельный файл** `zyablik.config.staged.json`
(не таблица в БД). Запись конфига и staged — атомарная (временный файл +
`rename`), lkg — простая ротация бэкапов (Pi-hole: `config_backups/` +
last-known-good при ошибке парсинга; AdGuard Home: temp+rename). БД не
используется: конфигурация — файл, смешение с БД создаёт два источника
правды (контрпример — Nginx Proxy Manager, issue #5690).

**Жизненный цикл staged:** staged — полный снапшот конфига (включая
`version`). Успешный Apply **очищает staged**; авто-откат и ручной rollback
также очищают staged (неприменённый конфиг больше не актуален). После
очистки `GET /api/config/stage` возвращает пустой diff. Ручной rollback
дополнительно снимает pending-маркер (см. «Rollback (ручной)»).

**Логирование (ADR-0029)** — на каждом этапе для диагностики:
`config.applied` (from→to, hash), `config.validate_failed` (поле+причина),
`config.pending` (маркер установлен, рестарт), `config.confirmed` (маркер
снят, ready), `config.rollback` (причина auto/manual, from→to),
`config.quarantine` (перемещение bad-файла), `config.import`. Уведомление
оператора — через web UI (`GET /api/config/status` + banner, ADR-0046).

### Bootstrap и миграция

- Команда `--generate-config` — CLI-флаг `app.js` (argv уже разбирается,
  `src/bot-platform/app.js:220`): генерирует первый `zyablik.config.json` из
  текущего окружения (для миграции существующего `.env`-стенда): управляемые
  настройки — в файл по маппингу ниже, секреты — как `$VAR`-ссылки на `.env`.
  Пишет в путь из `ZYABLIK_CONFIG` (по умолчанию `./config/zyablik.json`).
  При существующем файле — отказ (не перезаписывает); `--dry-run` печатает
  результат в stdout;
- Команда `--rollback-config` — CLI-флаг `app.js`: ручной откат к
  `zyablik.config.json.lkg` (восстановление + снятие pending-маркера +
  очистка staged). Для сценария восстановления без UI. Без lkg — отказ с
  понятной ошибкой;
- Env остаётся только как `.env`-слой (см. «Решение»): `ZYABLIK_CONFIG`,
  `NODE_EXTRA_CA_CERTS`, секреты и неизменяемая база. При отсутствии файла
  процесс стартует на дефолтах + `.env`-слой (обратная совместимость точки
  входа); управляемые env-переменные без файла также не используются.

блок и создал бы смешение: часть IdP-конфигурации в файле, часть в env.

бота (`MAX_BOT_TOKEN`, `METRICS_API_KEY`, `SESSION_SECRET`) получают
`$VAR`-ключи в файле, т.к. их статусом оператор управляет через UI.

### Версия формата и миграция

Конфиг-файл имеет служебный ключ верхнего уровня `version` (целое,
начинается с 1; при отсутствии считается 1). `version` не управляется UI и
не входит ни в одну секцию.

- `loadConfig` отказывается загружать файл с `version` **выше** текущей
  схемы (файл создан более новой версией софта) — fail loudly, авто-откат
  к lkg;
- При `version` **ниже** текущей — пошаговая миграция вверх (массив
  миграций, переносящий значения старых ключей). Миграция применяется в
  памяти при загрузке; после успешного pre-validate на Apply результат
  **записывается в файл** (version обновляется до текущей) перед рестартом.
  `.lkg` не мигрируется — хранит исходную версию; при rollback
  восстанавливается исходный файл и миграция применяется снова (миграции
  детерминированы и идемпотентны);
- `--generate-config` пишет текущую версию;
- Новые секции/ключи (новый плагин) миграции не требуют: файл без них
  валиден, применяются дефолты;
- Переименование/удаление ключа в схеме — это изменение `version` с
  соответствующей миграцией; «молчаливого» дропа старых ключей нет;
- Неизвестные ключи при совпадении `version` — warn + ignore (не ломать
  запуск из-за лишних полей, добавленных в файл вручную).

### docker compose

Файл конфигурации живёт вне image: каталог `./config` монтируется volume'ом,
секреты — docker secrets/env. Сам `docker-compose.yml` для бота — следующий
шаг; здесь зафиксировано только требование к форме хранения.

**Права на запись `./config`:** процесс пишет в каталог конфига
(apply/import/rollback/карантин/pending-маркер). В docker том монтируется
writable; в systemd каталог принадлежит пользователю сервиса
(WorkingDirectory, `systemd/zyablik-bot.service`).

## Почему файл, а не env

- Файл — единый валидируемый/диффуемый артефакт, которым может управлять UI;
- При compose файл монтируется volume'ом и не смешивается с переменными
  окружения контейнера;
- Один процесс загружает один файл — порядок приоритетов однозначен.

## Рассмотренные альтернативы

### Env остаётся источником правды (UI читает/пишет env)

Меньше переработки: UI редактирует `.env`, процесс уже всё читает.

Минус: `.env` — плоский бессхемный формат без секций; UI и процесс имеют
разные представления; при compose `.env` размазывается между compose и
процессом; экспорт/импорт «всей конфигурации» не имеет естественного
представления. Отклонено — это консервирует текущую проблему.

### Файл + env как слой переопределения любых ключей

Файл — источник правды, но env может переопределять любой ключ (в т.ч.
управляемые настройки).

Минус: два источника правды, неоднозначный приоритет, UI не может показать
«эффективное» значение без резолва env. Отклонено. `.env` остаётся только
как слой развёртывания (секреты + неизменяемая база); управляемые настройки
env переопределять не может.

### Секреты в файле открытым текстом

Проще всего: один файл со всем.

Минус: файл в volume может попасть в бэкапы/репозиторий; политика
`docs-leak-guard.test.js` запрещает литеральные секреты в репозитории.
Отклонено.

### Только env, конфигурация через git/GitOps

UI не редактирует, конфиг едет из git.

Минус: противоречит цели «оператор меняет конфигурацию через web UI».
Отклонено для MVP; git-backed история — future work (idea, «Not Doing»).

## Последствия

- `config.js` становится `loadConfig`; `createQueueMonitorConfig` читает свою
  секцию из общего результата;
- Появляются `--generate-config`, `zyablik.config.json`, `.lkg`;
- Apply = рестарт процесса: фиксируется контракт «процесс корректно
  завершается и перезапускается» (SIGTERM-хендлеры уже есть — ADR-0033);
- Env-переменные конфигурации из INSTALL.md/runbooks переводятся в секции
  файла (обратная совместимость: файл не обязателен при старте); `.env`
  остаётся для секретов и неизменяемой базы;
- Требование к UI и schema-driven управлению — ADR-0046;
- Миграция существующего стенда — через `--generate-config`.

## Тесты

- `npm test` (встроенный test runner) + новые unit-тесты: мерж
  defaults→файл→env, `$VAR`-резолвинг (включая fail-fast для секретов и
  reject литеральных значений), валидация секций (включая `nullable`),
  миграция версий файла, авто-откат (валидационный отказ, pending-маркер →
  confirmed/rollback по готовности), `--generate-config` воспроизводит
  поведение env-конфига;
- policy-тесты: `docs-leak-guard.test.js` — в репозитории нет литеральных
  секретов и внутренних адресов;
- Отсутствие новых внешних зависимостей (ADR-0015) проверяется
  существующими тестами зависимостей.
