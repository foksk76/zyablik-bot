# ADR-0048: Автоматизированный жизненный цикл разработки (automated dev lifecycle)

## Статус

Принято.

## Дата

2026-08-10

## Контекст

Разработка фактически идёт через feature/fix-ветки и PR (см. историю: ветки
`fix/ingress-*`, PR #25, #26), но процесс описан в `DEVELOPMENT.md` как
линейный цикл «выбрал задачу → внёс изменение → проверил → PR» без явной
кодификации ветвления и ролей. Не хватает формализации:

- изоляции задачи: ветка выделяется, но без единого правила («одна задача —
  одна ветка → PR»), стабильная версия в `main` не защищена от
  незавершённой работы;
- маркировки dev-следов и чистой сборки (ADR-0047 вводит механизм, но цикл
  не включает его);
- разграничения ролей в ревью: человек проверяет и синтаксис, и dev-мусор,
  и бизнес-логику одновременно;
- доставки в прод, привязанной к интеграции изменений.

То есть PR-цикл уже существует де-факто; ADR формализует его в единый
документированный жизненный цикл и добавляет недостающие стадии (маркеры,
чистая сборка, разделение ролей, доставка).

Ограничения проекта: нулевые внешние зависимости (ADR-0015), одна проверка
`npm test` (ADR-0004), CI уже запускается на PR и push в `main`
(`verify.yml`), PR-коллаборация есть (`opencode.yml`). Идея отточена через
`idea-refine`: `docs/ideas/automated-dev-lifecycle.md` (ревизия 2).

## Решение

Ввести единый жизненный цикл из шести стадий; цикл кодифицируется в
`DEVELOPMENT.md` и правилах `AGENTS.md`.

### 1. Инициация и изоляция задачи

Любая модернизация начинается с формализации идеи в проектной документации:
`docs/ideas/` (pre-ADR идея) → `docs/decisions/` (ADR, если меняется
архитектура/процесс/границы) → `tasks/sprints/` (задача с критериями
завершения). ИИ-агент на основе этой документации выделяет изолированную
**ветку** для фичи/фикса, не затрагивая стабильную версию в `main`. Слияние —
только через PR.

### 2. Синхронная разработка кода и документов

Код пишется по скилам, неразрывно связан с документацией: в коде
проставляются ссылки на задачи и ADR (например, `/* DEV-ONLY: ADR-0047 */`).
Вся отладочная информация, тестовые заглушки и исследовательский код строго
маркируются dev-маркером (ADR-0047).

### 3. Автоматическая сборка чистого продукта (предрелизная проверка)

Перед передачей работы на ревью агент прогоняет чистую сборку
(`npm run build:clean`, ADR-0047), которая вырезает маркированные dev-следы из
`src/bot-platform`. Формируется чистая версия продукта без логов разработки и
тестовых данных; policy-тест проверяет её. Прод-хост (вариант A, ADR-0047)
запускает именно эту чистую версию (`dist/clean/bot-platform/app.js`).

### 4. Контроль человека (Human-in-the-loop)

Агент формирует запрос на интеграцию (PR), прикладывая связи с обновлённой
документацией. Человек проводит ревью по чек-листу: бизнес-логика, цели
спринта, чистота концепции. Технический синтаксис и наличие dev-мусора
проверены автоматикой (CI + policy-тесты + гейт ADR-0047). Одобрение
человеком запускает интеграцию.

### 5. Бесшовный релиз и доставка

Интеграция в `main` автоматически запускает подготовку доставки: CI прогоняет
чистую сборку (ADR-0047) и проверяет прод-версию. Эксплуатационная документация
готовится человеком или агентом в том же PR до merge — CI не генерирует её
автоматически. **Состав операционной документации — конкретный набор файлов:
`docs/runbooks/*` (инструкции для дежурных) и запись в `CHANGELOG.md`.** Она
остаётся в репозитории (в `dist/clean/` документация не включается) и
используется на прод-хосте из git-чекаута при развёртывании; весь остальной
корпус документации (`docs/`, идеи, ADR, спринты) — dev-контекст, в
прод-процесс не вовлечён. Черновые материалы и идеи остаются в репозитории.
Деплой на боевой сервер — **полуавтоматический**: прод-хост разворачивается из
git (вариант A, ADR-0047), развёртывание запускается человеком по runbook.
Текущие `Dockerfile` и `docker-compose.yml` (ADR-0044/0045) обслуживают стенд,
а не прод-доставку; полная автоматизация доставки и Docker-схема для прода
(вариант C, ADR-0047) — future work, в данную задачу не входят.

### 6. Дихотомия сред (накопление знаний vs чистый прод)

- **Репозиторий** хранит полную историю: идеи, отказанные решения, спринты,
  код с dev-следами — контекст для ИИ-агента (включая codebase-memory
  knowledge graph) на следующих итерациях;
- **Прод** получает только исполняемый код без dev-следов и инструкции по
  эксплуатации.

## Почему ветки, а не правки в `main`

- Стабильная версия в `main` защищена от незавершённой работы: незаконченная
  фича не влияет на остальных;
- ревью привязано к точке слияния — PR;
- история dev-следов остаётся в ветках и в `main` (стадия 6: репо = полная
  история), прод получает чистую версию через сборку (ADR-0047).

## Почему полуавтоматическая доставка, а не полный авто-деплой

- Нет накопленного опыта стабильных релизов — авто-деплой без человека на
  первом этапе рискован;
- человек контролирует момент и порядок развёртывания на боевом сервере;
- автоматика берёт рутину (чистая сборка, проверка прод-версии, CHANGELOG),
  человек — решение «развернуть сейчас» и запуск runbook-а на прод-хосте.

## Почему чек-лист ревью узкий

Разделение проверок: автоматика отвечает за синтаксис и dev-мусор, человек —
за ценность (бизнес-логика, цели спринта, чистота концепции). Узкий чек-лист
снижает когнитивную нагрузку и время ревью; дублирование автоматики человеком
бессмысленно.

## Рассмотренные альтернативы

### Правки прямо в `main` (статус-кво)

Плюс: ноль изменений процесса.
Минус: незавершённая работа в стабильной ветке, нет точки ревью, нет
проверки прод-версии. Отклонено.

### Полный авто-деплой (GitOps, без человека)

Плюс: максимум автоматизации.
Минус: нет опыта стабильных релизов; риск неконтролируемого развёртывания на
боевом сервере. Отклонено для MVP; полу-авто доставка — промежуточный шаг к
нему (future work).

### Отдельный прод-репозиторий / ветка `release/*`

Плюс: жёсткое разделение сред.
Минус: избыточно для одного процесса на текущем масштабе; чистый артефакт
собирается из `main` по триггеру. Отклонено для MVP.

### Минификация/обфускация кода в проде

Плюс: защита кода.
Минус: проект Node, Apache-2.0; «минификация» здесь про удаление dev-следов,
обфускация противоречит открытому коду и ADR-0015. Отклонено.

## Последствия

- `DEVELOPMENT.md` описывает полный цикл: идея → ветка → код → чистая сборка
  → ревью → merge → доставка;
- `AGENTS.md` обновляется: правила ветвления, dev-маркеры (ADR-0047),
  порядок PR-ревью;
- `verify.yml`: шаг чистой сборки + policy-тест прод-версии (ADR-0047);
- Ревью человеком идёт по узкому чек-листу (бизнес-логика, цели спринта,
  чистота концепции);
- Релизы сопровождаются записью в `CHANGELOG.md`;
- Авто-деплой без человека и Docker-схема развёртывания (вариант C,
  ADR-0047) — future work, при накоплении опыта релизов.

## Тесты

- `npm test` — policy-тесты, включая `tests/clean-build.test.js` (ADR-0047);
- `verify.yml`: `npm run build:clean` + проверка, что чистая версия
  `dist/clean/` не содержит `DEV-ONLY` и dev-логов;
- процессные требования (ветки, маркеры, чек-лист) покрываются policy-тестами
  документации (`tests/docs-leak-guard.test.js`) и ревью человека.
