# ADR-0047: Dev-маркеры и чистая сборка (dev-only markers + clean build)

## Статус

Принято.

## Дата

2026-08-10

## Контекст

Разработка ведётся ИИ-агентами по скилам, но dev-следы (отладочные логи,
тестовые заглушки, исследовательский код) смешиваются с продуктовым кодом.
Единственная проверка — `npm test` (policy-тесты, ADR-0004); она не
гарантирует, что в релиз не попадёт dev-мусор. Ограничение: нулевые внешние
зависимости для bot-platform (ADR-0015) — чистая сборка должна быть
hand-rolled на stdlib Node.

Dev-контекст шире, чем dev-код: продуктивный код несёт ссылки на
документацию, которой в релизе нет — `ADR-NNNN` и `sprint-NN.md` в
комментариях (трассируемость решений) и в user-facing строках (описания
полей конфигурации, отдаваемые в Settings UI, ADR-0046). Проблема делится
на два слоя: комментарии удаляются чистой сборкой (слой 2), продуктовые
строки правятся в исходнике (слой 1).

Целевой жизненный цикл (idea: `docs/ideas/automated-dev-lifecycle.md`,
ревизия 2) требует: dev-следы строго маркируются агентом как «только для
разработки», перед ревью прогоняется автоматическая сборка, вырезающая
маркированные фрагменты. Маркировка — не ручная дисциплина, а механизм:
гейт CI проверяет результат чистой сборки и делает пропуск маркировки
заметным.

**Решение (интервью, 2026-08-10):** dev-маркеры **разрешены** в `src/` и в
`main` — dev-стенд запускается из `main` напрямую (с маркерами). Прод
разворачивается на отдельном хосте из git: checkout → `npm run build:clean`
→ запуск чистой версии (вариант A; вариант C — Docker — вторая схема, на
этапе не реализуется). Вырезание dev-маркеров (`DEV-ONLY`) применяется
**только к `src/bot-platform`**; вырезание doc-маркеров (`DOC-REF`) — и к
`src/bot-platform`, и к `src/queue-monitor`; чистая версия зеркалирует оба
дерева (см. «Содержимое dist/clean»).

## Решение

### Формат dev-маркера

- **Блочный** для многострочных фрагментов:

  ```js
  /* DEV-ONLY: <ссылка на задачу или ADR> */
  // ... отладочный код, заглушки, исследовательский код
  /* END DEV-ONLY */
  ```

- **Однострочный** для одиночных строк: `// DEV-ONLY: <ссылка на задачу или ADR>`.

Маркер обязан нести ссылку на задачу или ADR — по ней гейт валидирует, что
dev-след легитимен. Формат ссылки:

- ADR: короткая форма `ADR-NNNN` (например `/* DEV-ONLY: ADR-0047 */`) —
  резолвится в `docs/decisions/ADR-NNNN-*.md` (glob, ровно один файл);
- задача: `tasks/sprints/sprint-NN.md` — задачи ведутся спринт-файлами,
  отдельных файлов на задачу нет; допускается суффикс `#task-X.Y` (например
  `// DEV-ONLY: tasks/sprints/sprint-42.md#task-42.3 */`).

**Валидация ссылки:** `clean-build.js` при обработке маркера проверяет
существование целевого файла — `docs/decisions/ADR-NNNN-*.md` (по короткой
форме `ADR-NNNN`) или `tasks/sprints/sprint-NN.md` — и завершается с ошибкой,
если ссылка не найдена.
Это делает требование «легитимный dev-след» проверяемым, а не декларативным.
Описание формата и валидации фиксируется в `AGENTS.md` и `DEVELOPMENT.md`.

### Формат doc-маркера (`DOC-REF`) — слой 2

Ссылки на не-поставляемую документацию в комментариях (ADR, sprint-файлы,
прочее из `docs/` и `tasks/sprints/`) оформляются маркером `DOC-REF` —
«этот комментарий объясняет продукт через документ, которого не будет в
релизе». Маркер вырезается чистой сборкой, как `DEV-ONLY`, но помечает
только строки комментариев, не исполняемый код:

- однострочный: `// DOC-REF: ADR-0033 reclaim зависших строк после краха`;
- блочный: `/* DOC-REF: <ссылка> */ ... /* END DOC-REF */`.

Формат ссылки внутри маркера — тот же, что у DEV-ONLY (`ADR-NNNN` или
`tasks/sprints/sprint-NN.md`, допускается суффикс `#task-X.Y`); валидация
существования целевого файла выполняется в `clean-build.js` так же, как для
`DEV-ONLY`. `DOC-REF` обязателен для любой ссылки на документ в комментарии
`src/` — гейт чистой сборки считает немаркированную ссылку ошибкой
(см. «Гейт CI»).

### Чистая сборка

`scripts/clean-build.js` — hand-rolled Node-скрипт без внешних зависимостей
(ADR-0015):

- вырезает из исходников `src/bot-platform/**` блочные
  (`/* DEV-ONLY */ ... /* END DEV-ONLY */`) и однострочные
  (`// DEV-ONLY: ...`) фрагменты;
- вырезает из `src/bot-platform/**` и `src/queue-monitor/**` (слой 2)
  однострочные (`// DOC-REF: ...`) и блочные
  (`/* DOC-REF */ ... /* END DOC-REF */`) строки комментариев;
- формирует «чистую» версию продукта в `dist/clean/`, зеркалируя структуру
  `src/bot-platform` и `src/queue-monitor` (см. «Содержимое dist/clean»);
  результат не содержит dev-логов и тестовых данных.

Вырезание `DEV-ONLY` применяется только к `src/bot-platform`: webhook
`src/zabbix-media-type/max-webhook.js` остаётся единым файлом, деплоится
копированием в Zabbix без dev-маркеров; React UI (ADR-0034) имеет собственную
сборку `build:ui` — DEV-ONLY в UI не применяется. Вырезание `DOC-REF` (слой 2)
применяется и к `src/queue-monitor` (комментарии в `api/`, `auth/`, `db/`,
`ui/src/`), так как его файлы зеркалируются в чистую версию без изменений:
`src/queue-monitor` копируется целиком, но строки `DOC-REF` вырезаются в
процессе копирования. `src/queue-monitor` не модифицируется в репозитории —
чистая версия создаётся в `dist/clean/`.

**Содержимое `dist/clean/`:** чистая версия зеркалирует `src/bot-platform/**`
(обработанные файлы) и `src/queue-monitor/**` (копируются без изменений) с
сохранением относительной структуры. Кросс-ссылки между деревьями при этом
резолвятся: точка входа `app.js` загружает `../queue-monitor`, а
`src/queue-monitor/api/config.js` — `../../bot-platform/core/config`. Вне
`dist/clean/` остаются и доступны прод-хосту по тем же путям, что и при
запуске из `src/`:

- `node_modules/` — устанавливается в корне репо (`npm ci`), Node резолвит
  модули подъёмом по дереву директорий от `dist/clean/bot-platform/app.js`
  до корня — отдельный `node_modules` в `dist/clean/` не нужен;
- `config/` (ADR-0045) — конфигурация читается по абсолютному пути из
  `ZYABLIK_CONFIG` или дефолтного `./config/zyablik.config.json` относительно
  `WorkingDirectory` сервиса (корень репо), не из `dist/clean/`;
- плагины (ADR-0012) — загружаются из `src/bot-platform/plugins/`; поскольку
  `dist/clean/` зеркалирует весь `src/bot-platform`, плагины попадают в
  чистую версию автоматически.

Из `src/queue-monitor` в чистую версию исключаются dev-only артефакты UI:

- `ui/node_modules/` — dev-артефакт (устанавливается npm по мере надобности);
- `ui/dist/` — артефакт сборки;
- `ui/src/stories/` — Storybook-сториз (ADR-0036), dev-only;
- `ui/test/` — UI unit-тесты, dev-only;
- `ui/.storybook/` — конфигурация Storybook, dev-only;
- `ui/components.json` — конфигурация shadcn CLI (ADR-0036), dev-only.

Конфигурация сборки UI (`ui/vite.config.js`, `ui/tailwind.config.js`,
`ui/postcss.config.js`, `ui/index.html`, `ui/public/`, `ui/package*.json`)
остаётся в зеркале: в варианте A статика dashboard (`ui/dist`) либо собирается
на прод-хосте в `dist/clean/queue-monitor/ui/dist` (`npm run build:ui` +
копирование), либо dashboard работает без статики (`staticDir` опционален —
`src/queue-monitor/http-server.js`). Таким образом в прод-среду не попадают
сторонние dev-артефакты UI (сториз, UI-тесты, Storybook), а дихотомия сред
(ADR-0048, стадия 6) соблюдается и для `src/queue-monitor`.

Команда: `npm run build:clean` (новый script в `package.json`).

**Определение «dev-логов и тестовых данных»:** к ним относятся фрагменты,
помеченные `DEV-ONLY`, и только они. Продуктовые логи (safe logger, ADR-0013)
и runtime-уровни логирования (`bot.logLevel`, ADR-0045) **не вырезаются** и не
считаются dev-следами — их включение/выключение управляется конфигом, а не
сборкой. Чистая сборка удаляет ровно то, что маркировано; вне маркеров она
не модифицирует код.

### Слой 1: user-facing строки правятся в исходнике, а не сборкой

`DOC-REF` вырезает только комментарии. User-facing строки — описания полей
конфигурации (`description` в `config-schema.js`), которые отдаются в
Settings UI и `/api/config/schema` (ADR-0046), и `description` в
`ui/package.json` — **не трогаются сборкой**: это продуктовые строки, а не
dev-контекст. Их dev-след — сами номера ADR внутри текста. Такие номера
убираются **в исходнике**, не в сборке:

- из `description` в `config-schema.js` удаляются ссылки вида `(ADR-NNNN)` —
  текст остаётся продуктовым, ссылка переносится в `DOC-REF`-комментарий
  над полем схемы или в отдельное поле `docNote`, если оно нужно в API;
- из `description` в `ui/package.json` убирается `(ADR-0034)`.

Сборка оставляет user-facing строки без изменений — «чистый код релиза»
наследует чистый текст из исходника, а не результат вырезания. Это
гарантирует, что dev-контекст в UI не расходится между `src/` и `dist/clean/`
(иначе продакшен-сборка отличалась бы от исходника в видимом пользователю
тексте).

### Запуск прод-версии (чистый код без маркеров)

Прод разворачивается на **отдельном хосте** (не dev-стенд) из git:

1. **Вариант A (основной, реализуется):** прод-хост: `git pull` → `npm ci`
   → `npm run build:clean` → systemd-юнит запускает
   `dist/clean/bot-platform/app.js`. Минимум новой инфраструктуры; маркеры
   физически вырезаются на хосте перед запуском.
2. **Вариант C (Docker, future work):** multi-stage Dockerfile — build-слой
   выполняет clean-build, image содержит только чистую версию; прод-хост
   `docker pull && docker run`. Вторая схема развёртывания, перекликается с
   ADR-0045 (compose). На этом этапе не реализуется.

**Механика запуска (вариант A):** `WorkingDirectory` systemd-юнита остаётся
корнем репо (`/root/zyablik-bot`), `ExecStart` меняется на
`node dist/clean/bot-platform/app.js`. Node резолвит `require` подъёмом по
дереву от `dist/clean/bot-platform/` до корня, поэтому `node_modules/` из
корня репо доступен; относительный путь конфига (`./config/...`, ADR-0045)
резолвится от `WorkingDirectory`, а не от `dist/clean/`. Новой системы
сервисов не вводится — на прод-хосте существующий `systemd/*.service`
адаптируется (замена пути `src/bot-platform/app.js` →
`dist/clean/bot-platform/app.js`). В репо `systemd/*.service` остаются для
dev-стенда (запуск из `src/bot-platform/app.js` с маркерами) и не
переключаются на `dist/clean/`; прод-хост — отдельная машина со своей
конфигурацией systemd. Dashboard (queue-monitor) в варианте A стартует тем же
процессом `app.js` из `dist/clean/queue-monitor` (см. «Содержимое dist/clean»).

Итог по средам: `systemd/*.service` в репозитории — конфигурация **dev-среды**
(запуск dev-стенда из `src/`); в прод-среду поставляется только адаптированная
копия юнита, которой в репозитории нет.

Dev-стенд продолжает запускаться из `main` напрямую (`src/bot-platform/app.js`)
— с маркерами. Дихотомия: репозиторий хранит dev-следы, прод получает чистую
версию.

### Policy-тест на чистый артефакт

Новый policy-тест `tests/clean-build.test.js`:

- запускает clean-build;
- проверяет, что результат не содержит `DEV-ONLY`, dev-логов и тестовых
  данных;
- проверяет слой 2: в `dist/clean/` нет ссылок на не-поставляемую
  документацию (`ADR-\d{4}`, `sprint-\d{2}\.md`, `docs/`, `tasks/`) — как в
  комментариях, так и в строках;
- проверяет слой 1: user-facing `description` в `src/bot-platform/core/config-schema.js`
  и `src/queue-monitor/ui/package.json` не содержат `ADR-\d{4}`;
- проверяет работоспособность: ключевые модули чистой версии загружаются и
  экспортируют ожидаемые символы.

**Механика загрузки модулей чистой версии:** policy-тест вызывается из корня
репо (`npm test`), но относительный `require('./../src/...')` из `tests/`
не сработает для `dist/clean/` — тест грузит модули по **абсолютному пути**
от корня репо: `require(path.join(repoRoot, 'dist/clean/bot-platform', <rel>))`.
Внутренние относительные `require` внутри bot-platform резолвятся от самого
модуля (`__dirname`), а не от `tests/`, и поскольку `dist/clean/` зеркалирует
структуру `src/bot-platform`, они разрешаются корректно. Список «ключевых
модулей» — константа в тесте (например `core/config`, `core/logger`,
`app.js` без запуска сервера); проверка ограничивается загрузкой и проверкой
экспортов, без запуска процессов и сетевых вызовов.

`npm test` покрывает и чистую сборку — «чистая» версия является
полноправным продуктом тестирования.

### Гейт CI: прод-версия без dev-следов

В `.github/workflows/verify.yml` (и/или отдельном гейте на merge) добавляется
шаг: `npm run build:clean` + `tests/clean-build.test.js`. Гейт проверяет
**результат чистой сборки**, а не diff: маркеры разрешены в `src/` и в
`main`, но `dist/clean/` обязано быть свободным от `DEV-ONLY`, `DOC-REF`,
dev-логов, тестовых данных и ссылок на не-поставляемую документацию (слой 2);
user-facing строки — без номеров ADR (слой 1). Немаркированная ссылка на
документ в комментарии `src/` (без `DOC-REF`) тоже считается ошибкой гейта —
иначе правило «`DOC-REF` обязателен» не было бы проверяемым. Прод-схема
варианта A начинается с успешной чистой сборки — гейт гарантирует, что
прод-хост получит рабочую версию без dev-следов и dev-контекста.

## Почему блочный маркер, а не каталог `dev/`

- Маркер держит dev-след рядом с продуктовым кодом — виден контекст, для чего
  вставлен фрагмент;
- маркер несёт ссылку на задачу/ADR — каталог `dev/` такой связи не даёт;
- вырезание по маркеру не дублирует структуру исходников.

Физическое разделение (каталог `dev/`) остаётся альтернативой, отклонённой
для MVP: разрывает связь «код ↔ контекст» и требует зеркалирования структуры.

## Почему не env-флаг (`NODE_ENV=development`)

- env-флаг управляет только runtime-логированием; тестовые заглушки и
  исследовательский код при этом всё равно исполняются и остаются в релизе;
- «чистая» версия, собранная вырезанием, проверяема policy-тестом; версия,
  спрятанная за флагом, не имеет артефакта для проверки.

env-флаг не отвергается для управления логированием уровня
`bot.logLevel` (ADR-0045) — он решает другую задачу.

## Почему гейт на чистую сборку, а не запрет маркеров в `main`

Полный запрет `DEV-ONLY` в `main` (проверка diff) был отклонён при интервью:
dev-стенд запускается из `main` напрямую, и запрет маркеров в `main` лишил бы
его dev-следов — отладочные логи и заглушки полезны именно на dev-стенде.
Вместо этого гейт проверяет **результат чистой сборки**: `dist/clean/` обязано
быть без dev-следов. Так репозиторий хранит полную историю с маркерами
(стадия 6 жизненного цикла), а прод-артефакт остаётся чистым.

## Рассмотренные альтернативы

### Запрет dev-кода через дисциплину («просто не коммитить»)

Плюс: ноль инструментов.
Минус: полагается на дисциплину агента/человека, нет механизма проверки;
противоречит накоплению dev-следов в истории. Отклонено.

### Внешний инструмент вырезания/минификации (babel, strip-комментариев)

Плюс: готовые решения.
Минус: новые внешние зависимости противоречат ADR-0015. Отклонено.

### Проверка diff на `DEV-ONLY` в `main`

Плюс: простая проверка, `main` всегда без маркеров.
Минус: dev-стенд (запуск из `main`) теряет dev-следы; расходится с дихотомией
«репо = полная история». Отклонено при интервью — гейт смотрит на результат
чистой сборки.

### Переменная окружения как единственный механизм

См. «Почему не env-флаг» выше. Отклонено для dev-следов, оставлено для
runtime-логов.

### Слой 2: автоматический strip всех ADR-ссылок без маркера

Альтернатива «сборка сама находит и вырезает любой `ADR-\d{4}` в
комментариях, без маркера `DOC-REF`».

Плюс: не требует разметки ~80 существующих комментариев.
Минус: сборка молча меняет смысл немаркированных комментариев (нельзя
отличить осмысленную ссылку от случайного совпадения в строке), ссылки на
sprint/docs не покрыты общим правилом, гейт теряет проверяемость «ссылка
обязана быть маркирована». Отклонено: `DOC-REF` делает намерение явным и
проверяемым, как `DEV-ONLY`.

### Слой 1: вырезать ADR-номера из user-facing строк сборкой

Альтернатива «сборка удаляет `(ADR-NNNN)` из `description` и package.json
напрямую».

Плюс: не трогает исходники.
Минус: продакшен-сборка отличается от исходника в видимом пользователю
тексте — расхождение `src/` ↔ `dist/clean/`, которое не поймать diff-гейтом;
user-facing строка — продуктовый текст, а не dev-след. Отклонено: слой 1
правят в исходнике, чтобы «чистый код релиза» не расходился с `src/` в
пользовательских строках.

## Последствия
