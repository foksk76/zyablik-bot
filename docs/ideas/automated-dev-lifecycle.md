# Автоматизированный жизненный цикл разработки (automated dev lifecycle)

> Идея. Не ADR, не спецификация, не задача. Отправная точка для будущих ADR и
> декомпозиции в `tasks/sprints/`.
>
> **Принято:** ADR-0047 (dev-маркеры и чистая сборка) и ADR-0048
> (автоматизированный жизненный цикл разработки).
>
> **Ревизия 2 (idea-refine).** Идея отточена: выбрано ядро «dev-маркер →
> hand-rolled clean-build → policy-тест», ветки/PR и полу-авто доставка — как
> отдельные управляемые части; гейт CI проверяет результат чистой сборки.
> Изменения: HMW-формулировка, Assumption Audit (must/should/might), вариант 2
> инверсии в «Not Doing», явные названия артефактов и команд.

## How Might We (Problem Statement)

Как превратить разработку проекта в предсказуемый конвейер, в котором:

- ИИ-агент берёт на себя рутину: базовый код по скилам, разметку dev-следов,
  подготовку релизных артефактов;
- человек остаётся архитектором и контролером качества и не тратит время на
  ручную чистку кода и синтаксис скриптов деплоя;
- в прод попадает только чистый код и эксплуатационная документация, а весь
  черновик и исследовательский след остаётся в репозитории как контекст для
  следующих итераций?

Сегодня процесс зафиксирован в `DEVELOPMENT.md`, но работа ведётся прямо в
`main`, нет механизма изоляции задачи, нет маркировки dev-следов, нет шага
«чистой сборки» и нет автоматической доставки в прод. Человек вручную
проверяет и синтаксис, и чистоту концепции одновременно.

Единственная проверка — `npm test` (policy-тесты, ADR-0004). CI уже запускается
на PR и push в `main` (`.github/workflows/verify.yml`), а `opencode.yml` даёт
PR-коллаборацию. Ограничение: нулевые внешние зависимости для bot-platform
(ADR-0015), значит чистая сборка должна быть hand-rolled.

## Recommended Direction

**Ядро: dev-маркер + hand-rolled clean-build + policy-тест на чистый артефакт.**
Вокруг — формализация веток/PR и полу-автоматическая доставка. Весь цикл
кодифицируется в правилах репо (`AGENTS.md`, `DEVELOPMENT.md`) без внешних
инструментов сборки.

Ключевая ставка: dev-следы можно маркировать и автоматически вырезать так,
что «чистый» продукт остаётся работоспособным, а `npm test` проверяет и его.
Маркировка — не ручная дисциплина, а механизм: гейт CI проверяет результат
чистой сборки (`dist/clean/`), поэтому пропуск маркировки становится заметным
на прод-версии.

## Шесть стадий

### 1. Инициация и изоляция задачи

Любая модернизация начинается с формализации идеи в проектной документации:

- `docs/ideas/` — pre-ADR идея;
- `docs/decisions/` — ADR, если меняется архитектура/процесс/границы;
- `tasks/sprints/` — задача с критериями завершения.

На основе этой документации ИИ-агент автоматически выделяет изолированное
рабочее пространство (ветку) для новой фичи или фикса, не затрагивая
стабильную версию продукта в `main`. Слияние — через PR.

### 2. Синхронная разработка кода и документов

- ИИ-агент пишет код, строго следуя заданным паттернам поведения (скилам).
- Код неразрывно связан с документацией: в нём проставляются ссылки на задачи
  и архитектурные решения.
- Вся отладочная информация, тестовые заглушки и исследовательский код строго
  маркируются агентом как **«только для разработки»** (dev-маркер).

### 3. Автоматическая сборка чистого продукта (предрелизная проверка)

Перед передачей работы на ревью агент автоматически прогоняет сборку, которая
вырезает все маркированные dev-следы. Формируется **«чистая» версия продукта**,
не содержащая логов разработки и тестовых данных. Policy-тест проверяет, что
в чистой версии не осталось dev-маркеров.

### 4. Контроль человека (Human-in-the-loop)

- Агент формирует запрос на интеграцию изменений в основную ветку (PR),
  прикладывая связи с обновлённой документацией.
- Человек проводит ревью: проверяет соответствие бизнес-логике, целям спринта
  и чистоту концепции.
- Технический синтаксис и наличие dev-мусора уже проверены автоматикой
  (CI + policy-тесты).
- Одобрение человеком запускает процесс интеграции.

### 5. Бесшовный релиз и доставка

- Интеграция изменений в главную ветку автоматически запускает процесс
  подготовки доставки в продакшн.
- Система берёт только чистый код и эксплуатационную документацию (инструкции
  для дежурных, история обновлений — `CHANGELOG.md`), оставляя черновые
  материалы и идеи в репозитории.
- Деплой на боевой сервер — полуавтоматический: merge в `main` готовит чистый
  артефакт, развёртывание запускается человеком по runbook.

### 6. Дихотомия сред (накопление знаний vs чистый прод)

| Среда | Содержимое |
|---|---|
| Среда разработки (репозиторий) | Полная история эволюции проекта: идеи, отказанные решения, спринты, код со всеми dev-следами. Идеальный контекст для ИИ-агента (включая codebase-memory knowledge graph) при следующих итерациях |
| Продакшн-среда | Только исполняемый код без dev-следов и инструкции по эксплуатации. Никакого шума, планов или отладочных данных |

## Проекция на текущий репозиторий

> **Примечание (2026-08-10).** Раздел — проекция идеи на момент ревизии 2.
> Принятые ADR-0047/0048 уточнили отдельные пункты: scope маркеров расширен
> (`DOC-REF` для `src/bot-platform` и `src/queue-monitor`, слой 1 — user-facing
> строки правятся в исходнике), артефакт чистой сборки — `dist/clean/`,
> доставка — вариант A. При расхождении действуют ADR.

### 1. Dev-маркер

Формат: блочный комментарий `/* DEV-ONLY: <task или ADR> */ ... /* END DEV-ONLY */`
(и `// DEV-ONLY: <task или ADR>` для однострочных). Маркер несёт ссылку на
задачу/ADR — по ней чистая сборка и гейт могут валидировать, что след легитимен.
Scope: только `src/bot-platform` (webhook и React UI — вне dev-маркеров).
Зафиксировать в `AGENTS.md` и `DEVELOPMENT.md`.

### 2. Чистая сборка

`scripts/clean-build.js` (hand-rolled, без внешних зависимостей — ADR-0015).
Вырезает маркированные фрагменты, формирует чистую версию в отдельном каталоге.
Команда `npm run build:clean` (новый script в `package.json`).

### 3. Policy-тест на чистый артефакт

Новый policy-тест (в `tests/`): запускает clean-build и проверяет, что
результат не содержит `DEV-ONLY`, dev-логов и тестовых данных; существующий
`npm test` покрывает и чистую сборку.

### 4. Гейт CI: прод-версия без dev-следов

В `verify.yml`: шаг `npm run build:clean` + policy-тест, проверяющий, что
`dist/clean/` не содержит `DEV-ONLY`, dev-логов и тестовых данных. Маркеры
разрешены в `src/` и в `main` (dev-стенд запускается из `main` напрямую);
гейт проверяет результат чистой сборки, а не diff.

### 5. Изоляция задачи

Процесс ветвления: идея → ADR/задача → ветка → PR в `main`. Оформить как
часть `DEVELOPMENT.md` и правил `AGENTS.md`. Чек-лист ревью для человека:
бизнес-логика, цели спринта, чистота концепции.

### 6. Доставка в прод

Полу-автомат: merge в `main` → CI проверяет чистую сборку (ADR-0047) →
прод-хост разворачивается из git (вариант A, ADR-0047) по runbook →
запись в `CHANGELOG.md`. Docker-схема (вариант C) — future work; текущие
`Dockerfile`/`docker-compose.yml` (ADR-0044/0045) обслуживают стенд, а не
прод-доставку.

## Assumption Audit

### Must Be True (деалбрейкеры)

- [ ] Вырезание dev-маркированных фрагментов сохраняет рабочесть «чистого»
      продукта — проверяется policy-тестом на clean-build артефакте.
- [ ] Clean-build выполним без внешних инструментов минификации (ADR-0015) —
      ручной Node-скрипт достаточен.
- [ ] Гейт на результат чистой сборки (а не на diff) делает пропуск маркировки
      заметным до прод-развёртывания — проверяется в `verify.yml`.

### Should Be True (важно, но не фатально)

- [ ] Существующие `npm test` покрывают и «чистую» сборку, а не только
      исходный код.
- [ ] Ветки/PR не конфликтуют с текущей практикой правок в `main` — merge
      остаётся быстрым.
- [ ] `npm run build:clean` не замедляет рутинный цикл до неприемлемого.

### Might Be True (бонус, не блокер)

- [ ] Knowledge graph (codebase-memory) использует полную историю с dev-следами
      как контекст для следующих итераций.
- [ ] Автодеплой без человека окажется достаточно надёжным, чтобы убрать шаг
      «запустить runbook» — проверить после накопления опыта релизов.

## MVP Scope

Этап завершён, когда:

- Определён формат dev-маркера (`/* DEV-ONLY */`), он применяется в коде и
  описан в `AGENTS.md` + `DEVELOPMENT.md`;
- Есть `scripts/clean-build.js` + `npm run build:clean`, артефакт кладётся в
  отдельный каталог;
- Policy-тест проверяет чистую сборку: нет `DEV-ONLY`, dev-логов и тестовых
  данных; `npm test` покрывает её результат;
- Гейт в `verify.yml` проверяет результат чистой сборки (`dist/clean/`
  без `DEV-ONLY` и dev-логов) при PR/push в `main`;
- `DEVELOPMENT.md` описывает полный цикл: идея → ветка → код → чистая сборка
  → ревью → merge → доставка;
- PR-ревью человеком идёт по чек-листу, а не по синтаксису.

**Не является MVP:** автоматический деплой на боевой сервер без участия
человека, минификация/обфускация кода в проде, миграция исторических спринтов.

## Not Doing (and Why)

- **Авто-деплой без человека на первом этапе** — прод-деплой остаётся
  полуавтоматическим (merge в `main` готовит артефакт, деплой запускается
  человеком по runbook), пока не накоплен опыт стабильных релизов.
- **Минификация боевого кода** — проект на Node, Apache-2.0; «минификация»
  здесь про удаление dev-следов, а не про обфускацию. Обфускация противоречит
  открытому коду и ADR-0015.
- **Переписывание истории в `main`** — дихотомия сред не означает чистых
  коммитов; репозиторий хранит полную историю.
- **Учёт dev-маркеров в историческом коде** — маркировка применяется к новому
  коду; ретроспективная маркировка всех старых файлов — отдельная большая
  задача, отложена.
- **Инверсия «запрет маркеров в репо вообще» как основной механизм** — репо
  должен хранить dev-следы как контекст (стадия 6), dev-стенд запускается из
  `main` с маркерами. Гейт проверяет результат чистой сборки, а не diff.

## Open Questions

- Формат dev-маркера: блочный комментарий, отдельный каталог `dev/`,
  переменная окружения? — принята рабочая гипотеза (блочный комментарий), к
  подтверждению на ADR.
- Чистая сборка: модификация существующего `npm test` или отдельная команда
  (`npm run build:clean`)? — принята гипотеза (отдельная команда), к
  подтверждению на ADR.
- Где хранить артефакт чистой сборки: ветка `release/*`, каталог,
  CI-артефакт? — открыт.
- Нужен ли отдельный ADR на конвейер целиком или декомпозиция на несколько
  ADR (dev-маркеры, чистая сборка, delivery pipeline)? — **решено: два ADR** —
  ADR-0047 (механизм: маркеры + чистая сборка + гейт) и ADR-0048 (процесс:
  цикл и доставка).
